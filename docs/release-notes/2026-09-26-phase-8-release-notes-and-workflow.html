Release notes

8A. AI Usage & Cost

What is new

  • Every call to an AI provider is counted when it ends: the ones that answer and the ones that fail (in a fallback chain, each try is one call). It is counted in the single place all provider calls pass through, so no page, run or fallback is missed and nothing is counted twice.
  • Only numbers are kept, never text. No prompt and no answer is saved. A row holds counts per quarter of an hour, project, provider, model and task: calls, failed calls, time, tokens and cost.
  • Cost is shown only when it is really known. A call gets a cost only if it answered, went to a provider with a price, and reported its token counts. Groq and Gemini use a list price; a custom provider uses the two prices you type in Settings. Ollama or another model with no price is counted but shows — as cost, never a made-up 0.
  • New page: AI Usage & Cost. Tiles for calls, tokens, estimated cost and AI time; a bar for each day; tables by provider and model, by task, and (for admins, all projects) by project. Buttons choose This project or All projects, the number of days, and Refresh.
  • New routes: GET /api/v1/projects/:project_id/ai-usage (viewer role) and GET /api/v1/ai/usage (admin key).

Good to know

  • Counting starts when this version starts. Earlier calls are not in it, and a price that changes later does not change the cost of calls already made.
  • If writing a count fails, the AI call itself is never lost or slowed down.
  • Embeddings do not go through the router, so they are not counted.
  • New table ai_usage (migration 0023), created automatically when the server starts.

8B. API tests from an OpenAPI document

What is new

  • Give a document, get tests. Paste an OpenAPI 3.x or Swagger 2.0 document (JSON or YAML, up to 5 MB) or give its address. AIQA works out test cases by rules, with no AI and no cost. It only makes a case when the document says what the answer must be.
  • Five kinds of case: HAPPY (a valid request), NO_AUTH (no credential, expects 401 or 403), MISSING_REQUIRED (a required parameter left out), WRONG_TYPE (a value of the wrong kind) and NOT_FOUND (an id that does not exist).
  • Look before you run. Show the cases lists every case, operation by operation, with the request and the answer it expects. Nothing is sent to your API at that point. You can leave operations out.
  • Safe by default. Requests that change data (POST, PUT, PATCH, DELETE) are shown but are not run unless you tick the box. The box carries a warning that they are really sent.
  • Credentials are only references. You give a header name and the name of an environment variable on the AIQA server (it must start with AIQA_SECRET_ or AIQA_LOGIN_). The value is read when a request is made and is never stored, shown, or written to evidence.
  • A clear report. For each operation: what it came to, and for each case what was expected and what came back, in plain words (for example Status is one of 404: got 400). It also shows how many operations of the document were tested, the pass rate, and notes on what to know before trusting it. It can be copied as Markdown.
  • New page: OpenAPI Tests, with the list of earlier runs beside the form. The open run is in the address (?run=), so a link or a reload lands on it.
  • New routes: POST .../openapi/plan, POST .../openapi/runs, GET .../openapi/runs, GET .../openapi/runs/:id.

Good to know

  • A run is one ordinary execution of the project (one task for each case), so the normal policy, evidence and audit apply. A target AIQA may not reach is refused, as for any other test.
  • Two new actions were added to the closed plan language (ASSERT_STATUS_IN, ASSERT_BODY_SCHEMA) and a small JSON Schema checker checks response bodies against the document.
  • One new dependency: serde_yaml (with unsafe-libyaml in the lock file). It is used only to read YAML documents.
  • New table openapi_runs (migration 0024). Deleting a project deletes its OpenAPI runs.

8C. Scheduled Regression

What is new

  • Run the same cases again. A schedule repeats the cases a project has approved and run once. Nothing is compiled again and no AI is asked: the run repeats the same tasks the cases last ran as. It is an ordinary execution, so policy, evidence, audit and the Execution Hub apply.
  • Every run says what changed since the last time, case by case: REGRESSED (passed before, fails now), FIXED, STILL_FAILING, STILL_PASSING or NEW. Regressions come first. The run gets one verdict: REGRESSED, FAILING, PASSING, RUNNING or NOTHING_RAN.
  • Schedules: a name; how often (every 5 minutes up to every 31 days); an optional first run time; how many cases at a time (1 to 8); every case or one suite; and whether it starts by itself. A schedule that does not start by itself runs only when asked, which is how a CI job uses it. At most 20 schedules per project.
  • Cases that cannot be repeated are listed with the reason, for example approved, but not run yet or only simulated, not executed.
  • New page: Scheduled Regression, with Run now, Pause / Resume and Remove (asks first), the history of runs, and each run's report (?schedule= and ?run= are in the address).
  • New routes under .../regression/: scope, schedules (make, list, change, remove), schedules/:id/run, schedules/:id/runs, runs/:id.

Good to know

  • A background loop looks every 30 seconds for schedules that are due. It keeps the time of day (a nightly schedule stays nightly), and after downtime it makes one run, not a queue of missed ones.
  • It never piles a run on top of one that has not ended.
  • It runs as the API key that made the schedule. If that key is revoked, the schedule pauses itself and says why in its note.
  • Repeating a case leaves the case as it was (it is still EXECUTED).
  • New tables regression_schedules and regression_runs (migration 0025). Deleting a project deletes both.

8D. CI integration

What is new

  • JUnit XML. Add ?format=junit to the report of a regression run or an OpenAPI run. Every case is a test in the XML: <failure> for a case that failed, <error> for one that could not run to the end, <skipped> for one that was not run.
  • Wait in one request. Add ?wait=60 (seconds, at most 300) and the request comes back when the run has ended, or when the time is up. A job does not need to poll.
  • The result without parsing. Every report answer has the headers X-AIQA-Verdict and X-AIQA-Final.
  • An OpenAPI verdict. The OpenAPI report now has a verdict too: RUNNING, FAILING, PASSING or NOTHING_RAN.
  • Ready-made scripts: scripts/ci/aiqa-ci.sh (bash, curl, sed, grep, awk) and scripts/ci/aiqa-ci.ps1 (PowerShell). They start a run, wait, save the JUnit file, print the report in words, and exit with a code the build understands.
  • Docs and an example: docs/ci/README.md (every setting, and short examples for GitLab, Jenkins and Azure DevOps) and docs/ci/github-actions.example.yml.
  • On screen: Download JUnit beside Copy as Markdown on both reports, and a Use it from CI panel on every schedule with lines you can copy.

Exit codes of the script

CodeMeaning
0The result is acceptable: everything passed, or what failed is not what AIQA_FAIL_ON fails on.
1The build should fail on the result.
2There is no result: a setting is missing, the run could not be started or read, it did not end in time, or nothing ran.

Good to know

  • AIQA_FAIL_ON can be failing (default: fail on any failing case), regressed (fail only on a case that passed last time; regression only) or never.
  • The API key is read from the environment and is never a command-line argument. The script never prints it.
  • The CI job must be able to reach the AIQA address. A hosted runner cannot reach an AIQA on a laptop; use a self-hosted runner or an address that is open to it.
  • JUnit times are 0: the reports do not keep how long each case took.
  • Nothing new is stored for 8D. The XML is made from the report each time it is asked for.

Not built: 8E Mobile (Maestro)

Left out on purpose. Mobile tests need a real Android device or an emulator connected, both to write the code and to check it. Without one, any code would be untested. It is the next thing to do when a device is available.

How each part works

8A. From an AI call to a number on the page

1. Something asks the AITest generation, Autopilot, the gap check, and so on
2. The router calls a providerGroq, Gemini, Ollama, custom…
3. The call endsAnswer or failure: the count is taken here
4. A row is addedPer quarter hour, project, provider, model, task
5. The page adds it upTiles, days, tables

8B. From a document to a report

1. Give the documentPaste it or give an address, and say where the API is
2. Cases by ruleValid, no credential, missing, wrong type, not found
3. Show the casesNothing is sent yet. You choose what to run
4. RunOne execution, one task for each case
5. Check each answerStatus and body against the document
6. ReportPer operation, coverage, pass rate, notes

8C. From an approved case to "what changed"

1. A case is approvedIn the Test Case Generator or by Autopilot
2. Run once for realThe case becomes EXECUTED and remembers its run
3. A schedule is dueOr you press Run now
4. The same tasks run againNo AI, nothing compiled again
5. CompareWith the previous run of this schedule (or the run the case was copied from)
6. VerdictRegressions first, then the rest

8D. From a CI job to a red or green build

1. CI job startsRuns aiqa-ci.sh or .ps1
2. Start a runPOST a regression run or an OpenAPI run
3. WaitGET ...?wait=60&format=junit, again if not ended
4. Save the XMLThe CI shows each case as a test
5. Exit code0 go on, 1 fail the build, 2 no result
What the verdicts mean
VerdictWhereMeaning
RUNNINGbothThe run has not ended. The report shows what it has so far.
PASSINGbothEverything that ran passed.
FAILINGbothA case failed, or could not be run to the end.
REGRESSEDregressionA case that passed last time fails now.
NOTHING_RANbothThe run ended and no case ran (for example every task was cancelled).

Try it yourself

Each part below has steps and what you should see. They are written for a first manual test on your own machine.

Before you start

  1. Start AIQA: run start.bat in the project folder (or start the orchestrator and the frontend as in the README, section 15).
  2. Open the frontend in the browser (usually http://localhost:3000). Paste an API key, press Verify Connection. The first key is the bootstrap admin key printed when the orchestrator starts for the first time.
  3. Choose or make a project in the project selector at the top. the left menu now has OpenAPI Tests, Scheduled Regression and AI Usage & Cost

8A. See what the AI calls came to

  1. Open AI Usage & Cost. the tiles show zero, or the calls made since this version started
  2. Use something that calls an AI provider you have set up in Settings, for example generate test cases from a requirements document in the Test Case Generator, or start an Autopilot run.
  3. Go back to AI Usage & Cost and press Refresh. the calls, tokens and time went up; today's bar has grown; the provider and model you used has a row; the task (for example test generation) has a row
  4. Look at the cost column. a dollar amount for Groq, Gemini or a custom provider with prices; — for Ollama or any model with no price; a note under the tiles that says how many calls had no price
  5. Try 7 days / 30 days / 90 days. With an admin key that is not tied to a project, try All projects. the page reads again; All projects adds a table by project

8B. Test an API from its OpenAPI document

Use an API you are allowed to test (your own development or staging API is best). Like other AIQA tests, addresses on private networks may be refused by AIQA's safety check.

  1. Open OpenAPI Tests. Choose Paste it and paste a document, or Give its address and give the address of the document. Fill Where the API is if the document does not name the server.
  2. Leave all five kinds ticked. Leave Also run the requests that change data unticked for the first try.
  3. Press Show the cases. a list of operations and cases, each with the request and the answer it expects; the requests that change data are marked as not run; nothing was sent to your API
  4. Untick an operation you do not want, then press Run N cases. the page opens the report and looks at it every two seconds; a "running" badge shows until the run ends
  5. Read the report. tiles for cases run, passed, failed and not run; a verdict for each operation; for a case that failed, the reason in words (for example "Status is one of 404: got 400"); a line "N of M operations of the document tested"; notes
  6. Press Copy as Markdown and paste it somewhere. Press Download JUnit. a Markdown text on the clipboard; an XML file saved with one test for each case
  7. If the API needs a token: on the machine that runs the orchestrator set an environment variable such as AIQA_SECRET_MY_TOKEN to Bearer <the token>, restart the orchestrator, and in the form add the header Authorization with the variable name AIQA_SECRET_MY_TOKEN. the form refuses to run while the variable is not set, and says which one; once it is set, the "no credential" cases expect 401 or 403 and the others send the token

8C. Run approved cases again on a schedule

  1. You need cases that were approved and run once for real. In the Test Case Generator, approve a few cases and hand them off to a real executor (compile and execute), or let Autopilot do it. each case shows the status EXECUTED
  2. Open Scheduled Regression and press New schedule. Give it a name, keep every case, choose Every hour, and untick Start it by itself for the first try. a line under the form says how many cases would be repeated, and why some cannot (for example "approved, but not run yet")
  3. Press Make the schedule. the schedule opens and says "runs only when asked"
  4. Press Run now. the report opens; when the run ends the verdict shows "All passing"; each case says what it came to now and what it came to before (the first time it compares with the run the case was copied from)
  5. Make something break that a case checks (for example point the case at an address that now fails, or stop the app under test). Press Run now again. that case is at the top as Regressed with the reason, the verdict says "Regressions found", and the case says "passed last time, fails now"
  6. Fix it and press Run now once more. the case shows Fixed and the verdict goes back to "All passing"
  7. Try Pause and Resume, and Remove (it asks first). To see a run start by itself, make a schedule that is on, every 15 minutes, and wait: within about 30 seconds after it is due a run appears in its history marked "schedule".

8D. Use it from a CI job

  1. Make a key for the job. With the admin key, send POST /admin/api-keys with {"name": "ci", "role": "operator", "project_id": "<project id>"}. The key is shown once; keep it.
  2. Open a schedule in Scheduled Regression and open Use it from CI. five lines with your project id and this schedule's id already filled in, and a Copy these lines button
  3. In a terminal at the project folder (Git Bash, WSL or Linux) run the lines, with your real address and key: 
    export AIQA_URL="http://localhost:8080"
export AIQA_KEY="<the operator key>"
export AIQA_PROJECT="<project id>"
bash scripts/ci/aiqa-ci.sh regression <schedule id>
echo "exit code: $?"
    "started the regression run", then the report in words, then "the run ended: PASSING" (or REGRESSED), a file aiqa-junit.xml, and the exit code: 0 when it passed, 1 when the build should fail
  4. Open aiqa-junit.xml in an editor or a JUnit viewer. one test for each case; a failing case has a <failure> with the reason and, in its output, what changed since last time
  5. Try the other settings: AIQA_FAIL_ON=regressed (only new breakage fails the build) and AIQA_FAIL_ON=never. On Windows use powershell -File scripts\ci\aiqa-ci.ps1 regression <schedule id> with the same settings as $env:AIQA_URL and so on.
  6. Test an API from a CI job the same way: 
    bash scripts/ci/aiqa-ci.sh openapi https://your-api.example.com/openapi.json https://your-api.example.com
    the same flow, with the OpenAPI report and verdict (PASSING or FAILING)
  7. See the raw answer, with the two headers: 
    curl -i -H "Authorization: Bearer $AIQA_KEY" \
  "$AIQA_URL/api/v1/projects/$AIQA_PROJECT/regression/runs/<run id>?format=junit&wait=30"
    the XML in the body, and X-AIQA-Verdict and X-AIQA-Final in the headers
  8. On either report page press Download JUnit. the same XML saved as a file
More: every setting and short examples for GitHub Actions, GitLab, Jenkins and Azure DevOps are in docs/ci/README.md. A ready GitHub Actions example is docs/ci/github-actions.example.yml.

Database, dependency, settings

  • Migrations 0023_ai_usage, 0024 (OpenAPI runs) and 0025_regression run automatically when the orchestrator starts. They only add tables.
  • New Rust dependency: serde_yaml 0.9 (and unsafe-libyaml in Cargo.lock). No new frontend package.
  • No new AIQA environment variable. Credentials for OpenAPI tests use the existing AIQA_SECRET_* / AIQA_LOGIN_* convention. The CI scripts read AIQA_URL, AIQA_KEY, AIQA_PROJECT, AIQA_FAIL_ON, AIQA_JUNIT_FILE, AIQA_TIMEOUT_SECONDS, AIQA_OPENAPI_AUTH and AIQA_OPENAPI_UNSAFE on the CI side only.

How it was checked

  • Backend: 1,591 tests passed, 0 failed, 2 ignored on purpose (cargo test --lib). Clippy has no error. When every test runs at once on a very busy machine, two older timing-based tests (be12, be13) can fail; they pass alone and with fewer threads.
  • Frontend: 1,478 tests in 70 files passed, the type-check (npm run lint) is clean, and the production build (npm run build) works.
  • CI scripts: both scripts were run against a small stand-in server in 30+ situations each (pass, regression, failing, nothing ran, unknown verdict, timeout, a read that fails once, refusals, wrong key, server down, bad settings, the request body for an address and for a file). The PowerShell script was tried on Windows PowerShell 5.1 only.
  • Commands: cargo test --lib in services/orchestrator, and npm run lint, npm test, npm run build in forentend.

Limits and open points

  • 8E (mobile) is not built. See the release notes above.
  • OpenAPI tests only check what the document says. There are no login flows or OAuth handshakes; a credential is one header. Cases that need real data (a real id that exists) use an example from the document when it has one.
  • Regression repeats; it does not heal. If the application changed so much that a compiled case no longer fits, the case fails and shows as regressed. Use the self-healing features to change a case.
  • Only cases that ran once for real are repeated. Approved but never-run cases and cases that were only simulated are listed as "not repeated", with the reason.
  • The CI job must reach AIQA (address and network). AIQA's own safety check still decides which addresses it will test.
  • JUnit times are 0 because the reports do not keep per-case timing.
  • The PowerShell script was tried on Windows PowerShell 5.1. It is written for PowerShell 7 too, but that was not tried.
  • Some older timing-based backend tests (be12, be13, be18, test_29) can fail when the machine is very busy. They pass when run alone. This was true before Phase 8 too.
